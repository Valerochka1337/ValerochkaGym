# Exercise execution variants — implementation plan

## Goal

Implement the approved execution-variant flow (`AC-001…AC-020`): a user can maintain named variants of one base exercise, select one (or **«Без варианта»**) per routine row/workout section, and receive separate history, prefill, PRs and progress without losing offline, legacy, or Sheets data.

## Scope, non-goals, assumptions

- Scope: Room v8→v9, variant CRUD/archive, routine/active-workout selection and immutable snapshots, grouped performance data, navigation/display, and backwards-compatible Google Sheets import/export.
- Non-goals: structured grip/equipment fields, per-variant muscle maps/type/notes, historical reassignment, a combined “all variants” chart, new permissions/services/dependencies/logging.
- Assumptions: product brief is approved; nullable `variantSyncId` is only the storage/Sheets encoding of the explicit canonical **«Без варианта»** group (no fake variant row); old `Workouts` rows remain supported; exported exactness applies to completed sections/sets only (per AC-016); no product blocker exists.

## Current → target flow

`Room exercises/routine_exercises/workout_exercises → DAO → ActiveWorkoutRepository/UseCases → ViewModel StateFlow → Compose` currently keys prefill, PRs and statistics by `exerciseId`; workout import collapses sections by exercise name.

Target: `Room exercise_variants + nullable routine variantSyncId + workout sectionSyncId/variantSyncId/variantNameSnapshot → repository transaction → immutable UI state → Compose events`. Comparison identity is `ExerciseExecutionKey(exerciseId, variantSyncId?)`; routine records resolve only a variant owned by that exercise, while workout snapshots deliberately have no live variant FK. `WorkoutDao` projects the key into completed-set/analytics rows; statistics and PRs group by `(workoutId, key)`. UI always observes Room through repositories/DAOs and never owns durable selection state.

## Frozen architectural contracts

- **Variant SSOT.** `exercise_variants`: local ID, `exerciseId`, UUID `syncId`, current display `name`, canonical `normalizedName`, `isArchived`, monotonic `updatedAt`; unique `syncId`, `(exerciseId, syncId)`, and `(exerciseId, normalizedName)`. Normalize with `trim()` + `lowercase(Locale.ROOT)` before validation/write. Archive/restoration changes the same definition/version; no delete UI.
- **Routine ownership constraint.** `routine_exercises.variantSyncId` is nullable, durable (never a local ID), and is protected by the composite FK `(exerciseId, variantSyncId) → exercise_variants(exerciseId, syncId)` with `NO ACTION`; SQLite permits both child values null, which is **«Без варианта»**. This makes a cross-exercise UUID impossible at write time, including for `GymRepository.saveRoutineConfiguration` and import. If Room cannot generate the composite FK in v9, the fallback is a single `GymDatabase.withTransaction` validator used by *every* routine writer/importer plus a regression test for direct DAO rejection; do not silently drop ownership enforcement.
- **Workout snapshot invariant.** Every `workout_exercises.sectionSyncId` is nonblank canonical UUID and globally unique (unique index). Variant state is exactly either `(variantSyncId=null, variantNameSnapshot=null)` or `(canonical UUID, nonblank trimmed snapshot)`; no half state. It has no live variant FK, so imported history may have an unknown/archived definition but never lacks its valid snapshot. Start-from-routine, active add, allowed change, migration and Sheets import construct/validate the whole tuple atomically; legacy v8 rows receive fresh section UUID + null/null.
- **Transactions/cancellation.** `ExerciseVariantRepository` owns variant mutation validation and `GymDatabase.withTransaction`; `ActiveWorkoutRepository` owns start/add/change transactions. Change asserts active workout, matching base exercise and *zero completed sets*, then rewrites the snapshot and prefilled unfinished sets from the selected key atomically. ViewModel jobs live in `viewModelScope`, rethrow `CancellationException`; no new long-running work, permission, or service.
- **Explicit execution group.** Domain/UI/navigation use `ExecutionGroupToken`: `none` is the sole explicit canonical token for **«Без варианта»** and a canonical variant UUID represents a named group. Nullable Room/Sheets values decode to `none` at their boundary; no per-exercise fake DB record exists. The detail route is `exercise_detail/{exerciseId}/{executionGroup}` and *every* caller supplies a token; active/summary/history provide their section key, while catalog/no-context supplies `none`. `ExerciseDetailViewModel` validates/retains the token via `SavedStateHandle`; it never turns null/omission into “latest”. A malformed or legacy missing token normalizes to `none`, never a named group.
- **UDF/state.** Screen `UiState`s remain immutable `StateFlow` (`WhileSubscribed(5_000)`), with loading distinct from empty; commands/events are ViewModel methods plus buffered one-shot events. Only unsaved dialog text/expanded state uses `rememberSaveable`; selected persisted variants are Room truth.
- **DI.** Bind the repository once in `DataModule` as `@Singleton`; reuse existing database/DAO/Hilt scopes and `@ComputeDispatcher` for expanded stats Flow. No dependency/version-catalog change.
- **Sheets.** Append-only `ExerciseVariants` records use stable UUID, base exercise UUID, updated version, name and archive status. `Routines!A:M` is the exact current header: existing A:L plus `M=variant_id`; upgrade old A:K inserts L:M then writes `exercise_id,variant_id`, and current A:L inserts M. `Workouts!A:S` is the exact current header: existing A:N plus `O=section_id`, `P=section_position`, `Q=exercise_id`, `R=variant_id`, `S=variant_name_snapshot`. Upgrade current A:N inserts O:S. Insert after a recognised app header to shift user columns right; accept only known legacy/current exact headers and reject corrupt/manual headers before append. Ordinary retry and import rollback remain tested. Per PD-013, a lost network response after a committed column insertion is an accepted residual risk: no special durable detection/re-read-idempotence guarantee or test is required. Parser decodes legacy rows as explicit none/legacy grouped only when the new columns are absent. Configuration import applies definitions before routine snapshots; unknown/wrong-owner UUID is a transactional conflict—no name heuristic, no partial local mutation. Workout snapshots import with their name even if definition is missing. Current completed-set-only Workouts export is retained.
- **UI.** Exercise detail gains a variant-management section; selection is a cancellable Material sheet/dialog only when active variants exist, includes explicit none, 48dp targets and semantics naming base + variant. Use `GymCard`, `PillButton`, `MaterialTheme.colorScheme`, `GymMotion`, `gymHaptics`; no raw colours, animation, haptics, screenshots or charts redesign.

## Quality gates

- Always: single `:app`, Room SSOT/UDF, immutable `StateFlow`/buffered events, handwritten fakes, no logs/mocks/destructive migration/dependency.
- Room: handwritten `MIGRATION_8_9`, exported `9.json`, v8→v9 and supported v1→v9 migration tests; composite `(exerciseId,variantSyncId)` ownership and snapshot tuple invariant tests; transactional mutations/import rollback.
- Compose/navigation: loading/empty/error/content/cancel paths; lifecycle collection; 48dp semantic controls, non-colour status, TalkBack labels, `fontScale=2.0`, compact/medium/expanded/back/restoration. No image/screenshot inspection requested.
- Coroutines: repository transaction and ViewModel cancellation test; compute stats use existing `@ComputeDispatcher` and test scheduler/collector conventions.
- Sync/work: existing configuration worker remains idempotent and schedules stable definition UUID; test ordinary retry-safe dedupe. PD-013 excludes a lost-response column-insertion idempotence gate. No new WorkManager/service/permission/manifest gate.
- Final: run `:app:testDebugUnitTest`, then `:app:assembleDebug` once after stable diff. `assembleRelease` is not conditional here because no build/release-sensitive configuration changes; run it only if scope expands to one.

## Risks, questions, rollback

| Risk | Mitigation / rollback/data preservation |
|---|---|
| v9 DDL or section UUID migration corrupts identity | Test incremental/full migration and schema; nullable fields preserve legacy as none; backup/export remains usable. Release rollback must ship a forward migration, never destructive downgrade. |
| Lost Sheets response after column insertion | **Accepted by PD-013.** A retry can insert/shift new columns twice; no durable remote operation ID is introduced in this scope. Normal retries, legacy/current header handling, corrupt-header refusal and transactional import rollback remain covered. |
| Sheets format is manually edited or mixes versions | Only exact A:K/A:L/A:M Routines and A:N/A:S Workouts headers are recognised; upgrades insert after the app header; corrupt header rejects safely. Strict UUID/owner resolution rolls back configuration and reports error, never name-matches. |
| Workouts two same-name sections collapse | New parser groups by section UUID when present; AC-016 round-trip locks it down. Legacy remains inherently name-grouped and is explicitly treated as none. |
| Archived/renamed definition obscures history | Workout snapshot is immutable, while UUID remains statistics key; archive does not delete. |
| UI adds accidental chooser/loses selection on recreation | Show only for active variants; cancellation creates nothing; Room owns confirmed selection and route/SavedStateHandle owns only selected detail key. |

No unresolved product question blocks implementation. Gate P self-check: all ACs map to a task and command; named/none/default detail navigation and mixed-card labels are explicitly owned/tested; the single writer owns every overlapping choke point (including GymRepository/RoutineUpdate); Room/sync gates include composite FK, snapshot, normal header upgrade and rollback evidence; PD-013 deliberately excludes lost-response insertion idempotence; irrelevant permissions/services/release/chart-inspection gates are excluded.
