## Цель и граница текущей работы

Подготовить воспроизводимый запуск разработки по
[android-feature-implementation](../.codex/skills/android-feature-implementation/SKILL.md),
с отдельными ролями исследования, планирования, реализации, проверки и ревью.
Сейчас разрешены чтение, планы и синхронизация локальной main. Изменения приложения, тестов,
сборочной конфигурации, реализация серверных функций, commit/push/merge PR не выполняются.

Критерии подготовки:

- AC-001: локальная main совпадает с origin/main, текущая ветка и рабочие документы сохранены.
- AC-002: определены роли, владение файлами, переходы R/P/I/T/V и единый владелец Gradle.
- AC-003: архитектурные, UX и условные проверки привязаны к существующим правилам проекта.
- AC-004: первый совместный выпуск 01–02 имеет Feature Brief, план, трекер и явные открытые детали.
- AC-005: среда проверена без сборки; неподтверждённые свойства и будущие команды обозначены явно.

## Архитектурные и проектные правила

Приоритет: явные решения владельца → [AGENTS.md](../AGENTS.md) →
[ARCHITECTURE.md](../ARCHITECTURE.md) и [дизайн-система](../docs/design-system.md) →
существующие код/тесты → официальные рекомендации платформы. Устаревшие требования заменены
согласно §2б глобального плана. Противоречие фиксируется в Feature Brief; молчаливой смены контракта нет.

| Область | Обязательный подход и цель проверки |
|---|---|
| Слои | Один :app; Compose → ViewModel → domain/repository → data. UI не пишет напрямую в DAO или HTTP |
| Состояние | Room/существующий repository — источник сохранённых данных; UDF, immutable UiState, lifecycle-aware collection, StateFlow/WhileSubscribed по образцам проекта |
| Операции | Use case координирует действие; repository держит транзакционный инвариант; типизированный результат описывает ошибки и конфликт |
| Конкуренция | Отмена coroutine не маскируется ошибкой; тяжёлые Flow на @ComputeDispatcher; единственный WorkoutSetMutator для правок подходов |
| Сохранность | Рукописные миграции; UUID/FK/null/история и STANDARD сохраняются; составная запись атомарна, внешняя sync после commit |
| Повторы | Сохранение/синхронизация/подтверждение не размножают результат; владелец операции и восстановление заданы явно |
| DI | Существующие Hilt scopes/bindings; новые абстракции только при явной задаче и пользе для тестов |
| Масштаб изменений | Переиспользовать компоненты и аналоги; не добавлять слой, модуль, универсальный framework или библиотеку ради названия паттерна |
| Наблюдаемость | Ошибки доступны пользователю; не добавлять Log.*, мок-библиотеки или analytics SDK |

`ARCHITECTURE.md` содержит исторические описания Room v15 и более поздний раздел Room 16;
актуальную версию сверять с GymDatabase/схемами. Старое упоминание исключения debug-логирования
не отменяет запрет AGENTS.md. Будущий AI-контракт глобального плана не выдавать за текущий код.

## UX и доступность

Каждый UI-план описывает основной путь и loading/empty/content/error, валидацию, отмену,
повтор, Back, пересоздание экрана и состояние после неуспеха. Пользователь понимает результат
действия, сохраняет введённые данные после ошибки и не видит технические термины без необходимости.

- Применение предложений AI/тренера только после согласия; профиль необязателен; регистрационная
  карточка не прерывает подходы/отдых. Эти правила включаются только в затрагиваемые фичи.
- Material3/существующие компоненты; цвета MaterialTheme, токены GymMotion/GymHaptics, строки в Kotlin.
- Touch target ≥48dp, TalkBack label/state/action, fontScale 2.0, compact/medium/expanded, insets.
- Состояние нельзя передавать только цветом; жест имеет доступную альтернативу.
- Проверки по accessibility-дереву, Compose/UIAutomator/ADB. Снимки экрана и видео не создавать
  и не открывать без отдельного явного запроса. Это правило AGENTS.md выше рекомендации skill
  автоматически просматривать снимки AnalysisRenderTest.
- Версионные API и новые системные сценарии сверять с официальной документацией при research
  соответствующей фичи. Существующие ссылки quality-gates не являются доказательством нового API.

## Мультиагентный протокол

Каждый запуск получает компактный packet с `fork_turns: none`: запрос, slug, этапы, пути brief/plan/
tracker, AC/T, владение файлами, принятые решения, открытые вопросы, доступные команды и формат отчёта.

| Волна | Роль | Вход → результат | Запись / команды |
|---|---|---|---|
| R | android_feature_researcher, обычно один | Узкий вопрос → Feature Brief с доказательствами и AC | Только чтение; второй агент только для независимой области |
| P | android_feature_planner | Brief → T/AC, зависимости, файлы/владельцы, проверки | Только свои vibe/<slug>-plan.md и -plan-track.md |
| P strict | Независимый reviewer по правилам skill | Стабильный план → findings и Gate P | Только чтение; P0/P1 и разрыв AC/T устраняются до кода |
| I | android_feature_implementer, обычно один | Замороженный план → код и минимальные регрессионные тесты | Только назначенные файлы; targeted проверки после прекращения параллельных записей |
| T + V | tester и reviewer параллельно | Стабильный diff → доказательства AC и независимое ревью | Reviewer только читает; tester единственный запускает Gradle |
| Исправления | Исходный implementer | Подтверждённые findings одним пакетом → исправленный diff | Точечная перепроверка затронутых требований |
| Финал | Главный агент | Стабильный diff → полный unit suite и assembleDebug, итог трекера | Команды последовательно; без параллельного Gradle |

Два implementer допустимы только с зафиксированными общими контрактами и непересекающимися
файлами. Каждый писатель получает инструкцию: «Другие агенты работают в этом checkout; сохраняй
их изменения, не откатывай чужие правки, сообщай о выходе за ownership». Room entity/DAO/migration/
schema принадлежат одному владельцу. Навигация, Hilt, version catalog и version bump — одному
назначенному писателю. Родитель владеет интеграцией, Git, triage и коммуникацией с пользователем.

Fast path — research → planning → implementation → параллельная проверка. Strict добавляет
независимое ревью плана и усиленное ревью результата при schema/sync/contracts/security,
permissions/manifest/system components, background/process-death/concurrency или build/release.
Первый выпуск 01–02 идёт strict из-за транзакций, конкуренции и защиты STANDARD. В первом
выпуске один implementer владеет сквозным сценарием, чтобы не разделять запись программы и UI.
В проекте включены агенты и лимит 4 одновременных потоков; план укладывается в этот лимит.
Скилл предписывает Sol/high для strict-review. В текущем инструменте именованный профиль
android_feature_reviewer закреплён за Terra/high и не допускает model override. Для strict-review
использовать отдельный обычный агент с Sol/high и полным read-only контрактом reviewer; роль
по ответственности та же, без изменения файлов .codex или попытки неподдерживаемого override.
При следующем запуске сверить доступные профили заново; не подменять требуемое ревью молча.

Окончательная классификация выполняется в Gate R по фактическому scope. Организационная работа
16 сама по себе не запускает implementation/test waves. Обязательный bump версии не производится
во время подготовки; любое затрагивание build/release проверяется по strict-триггерам skill.

| Режим | Этапы | Условие |
|---|---|---|
| Кандидаты fast | 05, 09, 15 | Только UI/domain; 09 использует готовый контракт CAL-01, 15 — готовый контракт 14. Новая схема, согласия, concurrency или build/release переводят этап в strict |
| Research | 16 | Выход — выбранный объём; REC-01 оценивается отдельно после решения, не получает fast автоматически |
| Strict | 01, 02, 03, 04, 06, 07, 08, 11, 12, CAL-01, AI-01, CAL-02, 13, 10, 14, PLAN-01, 21, 23, 17, 18, 19, 20, 22, 24, 25, 38 | Персистентность/контракты, конкуренция, системная интеграция, права, AI/чувствительные данные или релизные изменения |

### Единственный владелец Gradle

| Момент | Владелец | Правило |
|---|---|---|
| Подготовка/планирование | Никто | Gradle не запускается |
| Один implementer | Implementer | Только targeted команды после согласованного изменения |
| Параллельные писатели | Никто | После их завершения родитель выполняет один общий targeted compile/test |
| Волна T + V | Tester | Reviewer читает; ранее успешные команды не повторяются без нового основания |
| Исправления | Назначенный implementer | Минимальная проверка findings, когда других писателей/Gradle нет |
| Стабильный финальный diff | Родитель | Последовательные full unit → debug build и применимые условные gates |

## Проверки при будущей реализации

Читать [android-quality-gates.md](../.codex/skills/android-feature-implementation/references/android-quality-gates.md)
и выбирать только релевантные проверки. JUnit4, рукописные фейки; ViewModel — MainDispatcherRule
и живой collector; Robolectric только для реального Android/DAO. Тесты сопровождают реализацию,
а не создаются отдельно от изменяемого поведения.

После стабильного diff приложения главный агент выполняет последовательно:

```bash
JAVA_HOME="$(/usr/libexec/java_home -v 21)" ./gradlew :app:testDebugUnitTest
JAVA_HOME="$(/usr/libexec/java_home -v 21)" ./gradlew :app:assembleDebug
```

До этого — только нужные targeted проверки по плану. При графиках добавить AnalysisRenderTest,
при schema — migration/full-path проверки, при manifest/dependencies/R8/release — соответствующий
release gate. Полный прогон повторять только после изменений/сбоев, которые обесценили результат.
Единственный плановый bump версии выполняется при завершении фичи с проверкой актуальной main;
01–02 — один совместный выпуск. P0/P1 не остаются открытыми; P2 исправляются или явно оформляются
как принятый остаточный риск, без автоматического одобрения агентом за владельца.
