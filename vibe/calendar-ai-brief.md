# Первая AI-тренировка в календаре — Feature Brief

Этап21 / #53-A. Зависимости: AI-01 Android/backend, CAL-01/календарь, заметки, базовый профиль и PLAN-01. Медицинские этапы17–20 и REC-01 не являются зависимостями. Пользователь поручил самостоятельно конкретизировать оставшиеся детали.

## Объём и приоритеты

Один будущий one-off план: backend собирает контекст, вызывает AI, проверяет ответ и создаёт предложение. Программа и календарный план возникают только через явное утверждение PLAN-01. Недельные планы, медицинские выводы, оценка готовности/восстановления и обещание «оптимальной» нагрузки сюда не входят.

Цель пользователя имеет первый приоритет; недавнее покрытие мышц — второй, внутри совместимых с целью вариантов. Не переопределять STRENGTH/MUSCLE_GAIN общей равномерностью покрытия. Неизвестная цель остаётся неизвестной; профиль можно пропустить. Тип упражнения не доказывает конкретный эффект: точная таблица goal preference и пояснение выбора фиксируются в Gate P как продуктовая эвристика.

## Контекст и границы

- Android отправляет намерение: future instant/IANA zone, выбранные gymIds, доступное время, явные exercise/equipment exclusions, приоритетные мышцы и добровольное текущее состояние/предпочтения. Он не отправляет историю, окончательный prompt или provider credentials. Сохранённые поля backend читает самостоятельно.
- Typed AI-01 Ready подтверждает owner/revision/catalogRevision после sync ACK. Capture под catalog→owner head; без DB lock во время provider HTTP; перед созданием предложения повторная авторизация/ревизии внутри той же транзакции, что internal proposal creation. Разрыв между final freshness check и записью запрещён.
- История — только завершённые тренировки и выполненные подходы с canonical exercise ID. Окно28 календарных дней в зоне планируемого занятия — инженерный интервал наблюдения, не критерий медицинской достаточности. При capture фиксируется `capturedAt`: интервал `[startOfDay(capturedLocalDate − 27 дней), capturedAt]` включает сегодняшнюю завершённую тренировку. Окно отсчитывается от capture, поэтому план на отдалённую дату не теряет всю недавнюю историю. Будущие факты исключаются. Нужны Clock/DST/boundary fixtures. Пустая история означает «нет наблюдений», а не нулевую потребность/полное восстановление.
- Для веса используется только наблюдение того же canonical упражнения в этом окне. Если его нет, inferred weightKg=null. Вес другого упражнения/мышцы/пола не переносится. Явная последующая правка пользователя допускается PLAN-01. Нет обязательной нагрузки на основе пола/возраста.
- Профиль: goal, experience, sex если задан, вычисленный возраст без даты рождения, частота, длительность, ограничения. Дополнительно доступная актуальная масса может читаться из существующей measurement SSOT только как отдельная разрешённая fitness-проекция с датой измерения; отсутствие массы ничего не блокирует. Это уточняет research: отсутствие зависимости от медицинского ledger не означает исключение согласованной владельцем массы тела. Не переносить весь InBody/medical payload.
- Выбранные залы и реальный инвентарь определяют доступность; profile equipment preferences её не заменяют. Поддержать личные и стандартные разрешённые упражнения. Unknown/archived/unavailable/excluded не могут попасть в готовый план.
- Учитывать релевантные workout/set notes и exercise hints как данные, не инструкции. В форме явно показать, что заметки используются; доступен отказ для текущего запроса. Отбор: заметки завершённых фактов из того же окна и подсказки только разрешённых кандидатов; сортировка по источниковому времени убыванию, затем kind и canonical ID. Максимум20 записей и16384 UTF-8 bytes текста; запись, не помещающаяся целиком, пропускается, строки не обрезаются посреди символа. В контексте видны источник/дата и факт ограниченного отбора, без сырого архива. Gate P закрепляет точные timestamp fallback для legacy и совместимость с health disclosure правилами.

Свободный текст ограничений передаётся как ограничение пользователю/модели, но не объявляется машинно доказанным запретом. Для программной проверки нужны явные выбранные exercise/equipment exclusions; их редактирование доступно до запроса. Ни названия, ни заметки, ни AI prose не могут ослаблять эти ограничения или авторизацию.

## Проверка и применение

До предпросмотра backend проверяет strict DTO/unknown fields, UUID, actual exercise type, availability, hard exclusions, конечные значения и per-type bounds PLAN-01. Технические max bounds не называются безопасной тренировочной дозой. Числовую политику inferred weights/объёма надо отдельно зафиксировать в плане и eval fixtures; нельзя принять generic max1e6 за достаточную проверку разумности рекомендаций. Ошибочный ответ отклоняется целиком с понятным повтором, без тихой замены упражнения.

Provider output/промпт/ошибки не сохраняются и не логируются. Только проверенное typed предложение получает durable version. Dismiss/reject/ошибка/owner change не создают routine/calendar records. Пользователь видит цель, состав, дату и источник, может отредактировать, затем утвердить одну идемпотентную операцию PLAN-01. Не запускать тренировку или Google I/O напрямую; CAL-02 реагирует на принятый синхронизированный план.

## Acceptance criteria

- AC-001: запрос только после Ready и валидного future slot/zone/gym/candidate set; ручное планирование доступно при недоступном AI.
- AC-002: owner/session/catalog/head races до/после provider создают ноль предложений; internal creator и freshness имеют общую транзакцию.
- AC-003: контекст backend-only содержит только разрешённые необходимые поля, nullable unknowns, точные источники/даты.
- AC-004: goal-first и coverage-second policy детерминированно проверяются на известных примерах; no-history не становится readiness.
- AC-005: нет наблюдения того же упражнения → все inferred strength weights null; данные другого упражнения/пола не меняют это.
- AC-006: missing optional profile/mass/history/notes не блокирует; профильный prompt следует принятому72h/token протоколу.
- AC-007: invalid DTO/type/UUID/equipment/exclusion/numeric/context → no proposal; пользователь получает error/retry.
- AC-008: cancellation/late response не сохраняют provider payload или неактуальное предложение; текущий owner проверяется во всех durable effects.
- AC-009: editable preview/apply через PLAN-01 создаёт одну программу+план, reject/back до apply — ни одной.
- AC-010: fontScale2/TalkBack/48dp/adaptive и loading/empty/error/retry/expired/accepted states соответствуют design-system.

## Карта реализации и проверки

Уточнение Gate R при перехвате 10.09.2026: `records` workout JSON уже содержит
`finishedAt`, canonical `exerciseId`, `isCompleted` и nullable `completedAt`; отдельная
история для AI не нужна. Root принимает существующий Android fallback
`WorkoutDao.observeCompletedSets`: время факта `COALESCE(completedAt, workout.startedAt)`.
Фильтр требует завершённую неделетированную тренировку и `isCompleted=true`, затем
применяет capture-window к времени факта; завершённая тренировка без выполненных подходов
не добавляет наблюдений. Gate P включает граничные/DST/future timestamps и bounded
backend projection: нынешний общий `findByUserIdOrderByKindAscIdAsc` не является
доказательством ограниченного чтения истории большого аккаунта.

Перед Gate P остаются точные fallback времени заметок/подсказок, таблица goal preference
с устойчивым tie-breaker и числовая политика с отдельными eval fixtures. Это задачи
исполнителя в принятом объёме, не разрешение использовать transport max1e6 как норму.
Нужны примеры goal-priority против coverage, unknown goal без подстановки, same-exercise
weight-or-null, UTF-8/whole-note cap и атомарный отказ всего предложения при numeric violation.
Новый typed calendar action/schema не должен переиспользовать boolean exercise/InBody branch.

Следующий research-pass предложил как инженерный вариант точное переиспользование наблюдённого
веса без автопрогрессии и отдельные небольшие лимиты формы one-off draft. Это **ещё не
зафиксированная числовая политика**: транспортные ограничения не являются нормами тренировки.
Предложенный исследователем жёсткий отбор типов по цели и обязательный prefix всего рейтинга
root не принимает без Gate P: тип сам по себе не доказывает соответствие цели, а такой prefix
может исключить полезный вариант и противоречить добровольным предпочтениям. Goal preference
должен оставаться явно описанной продуктовой эвристикой с проверяемым приоритетом, а не
необоснованным физиологическим запретом.

Backend: `AiContextReader`, `AiActionService`, provider/schema validator/controller DTO, internal TrainingProposalAiCreator; backend tests с fake provider и барьерами. Android: AI-01 repository/readiness, calendar VM/action, profile gate, PLAN-01 preview; никаких новых Room сущностей без отдельной необходимости. Контракт AI-01 расширяется аддитивно: старые exercise/InBody схемы не переопределяются. Один writer на backend, один на Android после backend acceptance; общий DTO/fixture сначала. Root final unit/debug, server check/bootJar и строгий T/V обязательны.

## Последующее уточнение root для Gate P

Ранжирование по goal preference относится только к порядку полного контекста
кандидатов. В нём допустимы группы предпочитаемых типов как явно описанная продуктовая
эвристика. Запрет обязательного prefix относится к выбору готового черновика:
AI не обязан выбирать первые N кандидатов или фиксированный seed; другие разрешённые
типы не исключаются. Детерминированно тестируется порядок контекста, а не обещание
физиологического результата или точного состава ответа модели.

Provider не генерирует weight/speed/incline. Вес добавляется из факта того же
упражнения или null; speed/incline остаются неизвестными null до пользовательской
правки. Ограничения остальных полей — только инженерный envelope черновика.
Current Android экспортирует legacy weightKg; optional actualWeightKg — правило
совместимости backend с будущим/другим клиентом, не утверждение о текущем producer.
