Дата: 10.09.2026. База: main/origin/main cc590a4. Этапы 01–02, issues #45/#46.
Статус Gate R: исследование завершено; Q-001 ниже остаётся продуктовой деталью перед реализацией.

Источник решений: [глобальный план](github-issues-implementation-plan.md), раздел #45 + #46.

## Цель, объём и неизменяемые решения

После «Готово» пользователь выбирает создание новой или перезапись текущей личной программы.
Обе ветки используют только фактически выполненные подходы, в порядке занятия: 4 planned / 3 done
дают 3 подхода. Создание получает новую идентичность и не меняет исходник; перезапись сохраняет
ID/syncId существующей программы. История выполненной тренировки не изменяется.

STANDARD не перезаписывается. По принятой семантике создания программа не имеет ограничений
по залам, restSeconds=null; перезапись сохраняет отдых оставшихся упражнений, исходные note,
origin и идентичность. Отдельный ранний диалог обновления заменяется единым сценарием после Done.
Сохраняется возможность выйти без изменения программ.

Non-goals: миграция Room, изменение схемы или правил оборудования, новые сервисы/worker-контракты,
гостевой режим, backend merge, AI, новая навигационная модель и исправления #44/#47 за пределами
необходимой регрессии. Единственный bump версии — при завершении общего выпуска, не сейчас.

## Приёмка

- AC-001: «Готово» открывает выбор до изменения программы; отказ/выход не меняет программу и историю.
- AC-002: создание сохраняет одну PERSONAL-программу с новым operation syncId, выполненными
  подходами, restSeconds=null и без routine_gyms; исходник не меняется.
- AC-003: перезапись существующей PERSONAL-программы атомарно заменяет план выполненными
  подходами, сохраняет ID/syncId, связи с залами и отдых совпавших упражнений; пример 4→3 покрыт обеими ветками.
- AC-004: STANDARD/удалённый/отсутствующий источник не перезаписывается; защита в UI и внутри
  транзакции. Создание новой остаётся доступным при наличии выполненных подходов.
- AC-005: success/read-only/not-found/conflict/failure различимы; CancellationException не
  маскируется. Ошибка после commit при планировании sync не вызывает повторное создание.
- AC-006: повтор confirm и восстановление сохранённого состояния не создают дубль; черновик
  и operation identity восстанавливаются. Не обещать устойчивость произвольной force-stop сцены
  через один SavedStateHandle: конкретный предел восстановления должен быть явным в плане.
- AC-007: при нуле выполненных подходов существующая программа не очищается и пустая не создаётся
  молча. Точный UX — Q-001, не утверждён.
- AC-008: dialog/error/loading/Back сохраняют ввод и понятное состояние; есть семантика действий,
  targets ≥48dp, fontScale 2.0 и адаптивность по действующей дизайн-системе.

## Кодовые основания и переход

Пути ниже относительно app/src/main/java/com/valerochka1337/valerochkagym/.

| Текущее поведение | Целевое поведение / аналог |
|---|---|
| ui/summary/WorkoutSummaryViewModel.kt загружает снапшот и hasDiverged запускает ранний update dialog | Единый state machine выбора после Done; существующие Mutex, SavedStateHandle operation UUID и Channel переиспользуются |
| domain/RoutineUpdateUseCase.kt отдельно пишет родителя и детей, не проверяя origin | Typed атомарная операция через GymRepository; домен не дублирует транзакционный механизм |
| domain/SaveCompletedWorkoutAsRoutineUseCase.kt уже фильтрует isCompleted и сортирует position/setIndex | Сохранить mapper/пустые gym IDs/создание с новым ID; переиспользовать вместо второй реализации |
| data/GymRepositoryImpl.saveRoutineConfiguration — database.withTransaction и idempotent replay syncId | Аналог атомарной записи, availability checks и post-commit scheduling |
| data/backend/CatalogSchema.kt защищает STANDARD SQLite-триггерами | Триггеры не менять; перед записью возвращать понятный read-only результат |
| ui/navigation/GymNavGraph.kt уже обрабатывает onDone | Проверить путь без переписывания navigation graph |

WorkoutEntity.routineId использует SET_NULL; история не переключается на созданную копию.
RoutineEntity.syncId уникален, updatedAt обновляется существующим withNextUpdatedAt. Проверка
источника нужна в транзакции: после открытия диалога он может быть удалён или стать STANDARD.
Availability validation сохраняется. Многошаговая запись не оставляет частично очищенных детей.

Уточнение strict review: одного expectedUpdatedAt недостаточно, поскольку текущие DAO допускают
изменение дочерних записей без обновления родителя. Перед перезаписью сравнивать полный исходный
aggregate, включая подходы/отдых и связи с залами; конкурентная child-only правка вызывает Conflict.
Полный ожидаемый результат используется для безопасного replay без повторной записи. Каноническое
представление и тесты зафиксированы в delivery-плане; schema/журнал операций не добавляются.

## Владение и тестовая поверхность

Один будущий implementer: summary ViewModel/Screen, при необходимости
ui/components/SaveWorkoutAsProgramDialog.kt, оба use case, domain/GymRepository.kt,
data/GymRepositoryImpl.kt, минимальный RoutineDao запрос при необходимости. CatalogSchema,
navigation и worker контракт — чтение/регрессия; изменение scope требует отражения в плане.

Основные тесты относительно app/src/test/java/com/valerochka1337/valerochkagym/:
ui/WorkoutSummaryViewModelTest.kt, domain/SaveCompletedWorkoutAsRoutineUseCaseTest.kt,
domain/RoutineUpdateUseCaseTest.kt, data/GymRepositoryImplTest.kt. Реальная Room подтверждает
rollback, STANDARD и FK; рукописные фейки — VM/domain; живой collector обязателен для stateIn.
Точные T/файлы/команды закрепляет planner. Тесты здесь не выполнялись.

## Gate и открытая деталь

Strict: транзакционная запись, конкурентный confirm/изменение источника, idempotency,
восстановление UI и post-commit scheduling. Миграция не предполагается, но проверяется по diff.

Q-001: при нуле выполненных подходов показывать объяснение или сразу выходить по «Готово»?
Рабочая рекомендация исследователя — обычный выход без пути сохранения; это не принятое решение.
До ответа план может быть подготовлен с явной развилкой; нельзя выдавать Gate P за безусловное
разрешение реализовать этот UX. Принятые семантика 4→3 и защита STANDARD не переоткрываются.

## Старт реализации по поручению владельца

Владелец разрешил автономно реализовать весь согласованный план, выполнять Git-публикацию и
проверить успешный релиз. Прежний статус «только подготовка» выше — история подготовки.
Q-001 разрешён исполнителем в рамках этой делегации: при нуле выполненных подходов «Готово»
выходит без сохранения/перезаписи программы; завершённая история остаётся. Это сохраняет
существующие данные и не навязывает пустую программу. Gate P допускает реализацию.
