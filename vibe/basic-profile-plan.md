# Базовый профиль и общий контракт личного контекста (#50-A/#50-B, этапы 14–15)

Slug: `basic-profile`. План строгого пути: меняются Room, переносимый sync-контракт, owner-изоляция и граница AI. Он реализуется после этапов Google 08, guest-sync 12, CAL-01 и #9, чтобы не угадывать версию схемы и не конфликтовать с capability-слоями.

## Цель, scope и допущения

Владелец добровольно ведёт один базовый профиль: цель, пол, дату рождения, опыт, плановую частоту и длительность, предпочтения оборудования и свободные тренировочные ограничения. Профиль синхронизируется как один owner-scoped record; перед реальным AI-действием приложение изредка предлагает заполнить минимально полезные поля.

Не входят: вес, InBody, обхваты, OCR/PDF/фото, диагнозы/травмы/лекарства, клинические выводы, питание, trainer access, Google Sheets/Calendar, новый permission/worker/dependency и AI-рекомендация как продуктовая фича. `body_measurements` остаётся единственным хранилищем измерений.

Предполагается, что #51 уже даёт durable `GUEST/CLAIMED/OWNED`, #AI-01 даёт серверную AI-boundary, а backend может добавить новый kind без изменения legacy-v2/v3. Если их фактические contracts отличаются, T-001 фиксирует совместимую поправку до кода.

## Целевой поток и замороженные контракты

```text
ProfileScreen → ProfileViewModel → ProfileRepository → Room profile + profile_equipment (transaction)
  → SyncSchema invalidation → BackendSync snapshot/outbox
  → capability(profile) accepted → backend owner-bound record / ACK baseline

AI entry → AiProfilePromptGate → owner-scoped DataStore decision
  → (Fill: ProfileScreen; Continue/Disable: consume token once) → #AI-01 backend request
  → backend reads synced profile, computes UTC age → minimal provider context
```

**SSOT and identity.** Room owns profile content. `ProfileEntity` is keyed by a non-secret scope (`GUEST` or current authenticated owner ID) and has exactly one row per scope; `ProfileEquipmentPreferenceEntity(scope,equipmentId)` is its cascade child. The active local scope is the only profile exposed to UI/sync. Guest is local-only until #51 claim; transfer is an existing owner-state transaction extended to rekey guest row/children to B, assign deterministic B `syncId`, and retain one B row by applying server-wins if B already has one. A B→C switch clears B personal profile along with other personal data; standard catalog is untouched.

**Portable record.** Canonical key is `profile:<syncId>`. Payload has all fields, including nullable ones as literal JSON null: `schemaVersion`, `syncId`, `updatedAt`, enums, `birthDate`, numeric values, `manualConstraints`, and sorted `equipmentIds`. All timestamps are epoch milliseconds UTC. `PortableData.apply` validates then atomically replaces the current scope’s singleton and full child set. Existing measurement kinds stay byte-for-byte compatible. A profile tombstone is never valid: backend rejects `deleted=true` before the idempotency ledger/revision; client treats an incoming profile tombstone as a protocol failure and preserves Room row/children, baseline and outbox. Clearing is a retained empty profile snapshot, avoiding old-client delete inference.

**Capability and server compatibility.** Client sends `X-Gym-Capabilities: profile` on every sync read/write alongside other accepted capabilities. The accepted intersection is cached per owner, cleared on owner change, absent header or downgrade. Before cursor construction the backend hides profile for non-capable callers; the client filters profile before snapshot/outbox capture. An unaccepted dirty profile/outbox stays unchanged and pending, never sent/rebuilt/discarded. The same preservation applies to a previously ACKed clean profile: accepted→absent/downgraded capability must leave its Room row/children, acknowledged baseline and any outbox byte-for-byte intact; absence is never a remote delete. A later accepted full refresh is the only operation that can update it. Backend rejects a profile POST without capability before idempotency ledger or revision mutation; capable mixed batches remain atomic. Old reads omit profile only; they do not cause its delete. The matching canonical JSON fixture is byte-identical in `vibe/`, Android tests and backend tests.

**Validation and privacy.** Android and backend enforce the same enums, bounds, ISO date and code-point count. No inference from history/InBody is allowed. At #AI-01 request time backend reads only the authenticated owner’s committed synced profile, derives `ageYears` using UTC, and sends the provider goal/sex/experience/frequency/duration/equipment/manual constraints plus age years when present. It never sends `birthDate`, raw owner ID, measurements or unsynced local profile. Manual constraints are unstructured training text and have no clinical interpretation.

**Prompt transaction.** `SettingsRepository` owns `ai_profile_prompt.<scope>` state: disabled, lastShownAt, reservationToken, pendingKind and non-sensitive prompt config version. Eligibility first commits only a reservation token before attempting UI emission. The dialog acknowledges actual display in a second atomic edit, writing `lastShownAt` only when it has become visible; a death after reservation but before display clears the reservation without counting a show. Fill, Continue and Disable atomically consume/clear the token before navigation/effect; duplicate callbacks/stale token do nothing. A process death at any pending/consumed point clears the pending state and never restores a decision UI or executes AI automatically: the originating action exposes retry when still alive, otherwise the user explicitly re-enters it. This is at-most-once, not an exactly-once delivery guarantee. Fill also consumes before navigation. Continue and Disable execute their live continuation once; a death after consumption but before effect may require manual retry. `ProfilePromptGate` owns this policy with injected clock; ViewModels only render immutable state/events. There is no profile write on Skip/Disable and no prompt during active workout.

## Quality gates, risks and rollback

Relevant gates: Room handwritten incremental plus supported full migration/schema; transaction/fault tests around singleton+children, claim and outbox; capability filtering before pagination/ledger; WorkManager/outbox cancellation/idempotency; Hilt scope; DataStore recreation; Compose validation/loading/empty/content/error, TalkBack, 48dp, font scale 2.0 and adaptive width. No manifest, permission, foreground service, chart, dependency or release-only gate applies. `assembleRelease` is required only if implementation introduces a release-sensitive build/manifest/dependency change.

Risks: Room and DataStore cannot commit atomically; the reservation/shown-ack/token protocol avoids duplicate requests but may require a user retry after a process death. Guest-to-owner rekey must run inside #51’s owner transaction or data can leak. A missing capability header must retain rather than rebuild profile outbox. `updatedAt` alone cannot decide profile conflicts: server wins by explicit kind policy. Rollback is forward-only for migrated data; empty profile snapshots and unaccepted durable outbox are preserved, and no destructive downgrade or profile duplication is permitted.
