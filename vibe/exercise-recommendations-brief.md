# Локальная замена недоступного упражнения — Feature Brief

Этап 16 / REC-01, #11. Решение D-006 исполнительного трекера конкретизирует условный объём: предложить замену в редакторе программы при несовместимости с выбранными залами. Пользователь поручил самостоятельно завершить все доработки; дополнительное согласование MVP не требуется.

## Границы и основания

- `domain/GymRepository.kt` и `data/GymRepositoryImpl.kt:observeAvailableExercises` уже определяют пересечение доступности всех выбранных залов. Инвентарь и legacy membership остаются единственным источником доступности.
- `data/db/entity/ExerciseEntity.kt` содержит тип, stable syncId, archived и needsMuscleMapReview; `ExerciseMuscleEntity` хранит роли 100/50/0. `ExerciseMuscleDao.observeAll` даёт карту для чистого расчёта.
- `ui/routine/RoutineEditorViewModel.kt` уже вычисляет conflictingExercises и атомарно сохраняет draft через GymRepository. `RoutineEditorScreen` — место явного выбора замены.
- Работа локальная, доступна гостю; AI, backend, новые таблицы и изменение активной тренировки не нужны. Нет утверждения о медицинской эквивалентности упражнений.

## Продукт и алгоритм

Для конфликтующего упражнения показать «Подобрать замену». Кандидат доступен во всех выбранных залах, того же типа, не архивный, не входит в текущий draft и имеет проверенную карту мышц. Неизвестные требования оборудования исключаются даже при legacy membership. Без выбранного зала предложить сначала выбрать зал; без достоверной исходной карты показать объяснение и обычный ручной выбор.

Детерминированный расчёт: только положительные роли, хотя бы одна общая первичная мышца. Ранжировать по взвешенному Jaccard `sum(min(role))/sum(max(role))`, затем количеству совпавших первичных мышц, затем syncId. Для сравнения дробей применять целочисленное перекрёстное умножение. Первые пять результатов; объяснять общие первичные мышцы и доступность, не показывать процент как физиологическую точность. История нагрузки не используется: она не доказывает взаимозаменяемость и не переносит вес между упражнениями.

Выбор меняет только соответствующую строку несохранённого draft. Сохраняются позиция и количество подходов, но все параметры подходов и отдых очищаются; это явно сообщается перед применением. Запись программы происходит только существующим «Сохранить». Отмена ничего не меняет. Перед применением повторно сверяются исходная строка, выбранные залы, редактируемость и текущая доступность; устаревший выбор просит обновить список.

## Acceptance criteria

- AC-001: guest/offline получает локальный список без AI/сети, только для редактируемой программы.
- AC-002: фильтры всех залов, equipment unknown, archived, type, duplicates и неподтверждённых карт соблюдаются; отсутствие кандидатов объяснено.
- AC-003: детерминированный top-5 и tie-break доказаны примерами, нулевое пересечение исключено.
- AC-004: выбор меняет только draft, явно очищает параметры, сохраняет количество/позицию; отмена и Back не записывают данные.
- AC-005: смена зала, каталога, строки или read-only состояния инвалидирует открытый выбор; существующий transactional save повторно проверяет доступность.
- AC-006: расчёт выполняется через flowOn(@ComputeDispatcher), UI использует существующие токены/семантику, доступен TalkBack и крупный шрифт.

Проверки: чистые ranker fixtures; VM с ручными фейками и активным коллектором; Compose для выбора/отмены/empty state и крупных шрифтов; существующие сохранение и active-workout остаются неизменными. Один Android writer владеет feature-кодом, DI и единственным инкрементом версии; Room-миграция не планируется. Gate P должен закрепить конкретные файлы и тесты до реализации.
